## 1. 项目概况

| 项 | 值 |
| --- | --- |
| 目标 | 以用户家三花猫照片为形象基底，做一个像素风桌面宠物，可 exe 启动，支持插件扩展 |
| 工作目录 | `F:\desktop-pet` |
| 技术栈 | **Electron 33 + TypeScript**（用户确认） |
| 插件形态 | **外部插件目录 + 热加载**（用户确认）：每个功能一个文件夹，丢进 `plugins/` 即生效，不重打包 exe；宿主仍是后续规划 |
| 形象 | **chibi 高密度精修版**，原生 **76×68 px**，22 色，7 组 / **33 帧**动画 |

| 交互补丁 | 程序内可**暂停 / 继续**、**隐藏 / 显示**；单击摸头、双击生气、拖拽携带，暂停不加暗色遮罩或角标 |

| 拖拽手感 | 内容区坐标 + 递增位置序号，丢弃过期原生回传；完整回归 `drag-pointer` 漂移 1px、`window-sync` 最大偏差 1px |

| 朝向 | `facing`：**1 = 朝右、-1 = 朝左**；原生贴图朝左，故朝右才镜像 |

### 形象规格变更

原生尺寸从 **72×68 变为 76×68**（左右各加 2px 边距），这是为修掉"待机多余黑线"所做的必要改动：
尾巴贴到画布边缘会被裁切，描边就出现在边界上。所有测试基线与 `preview/pet.json` 已同步更新。

## 2. 关键决定与否决记录

| # | 决定 | 理由 / 用户原话 |
| --- | --- | --- |
| D1 | Electron + TypeScript，而非 Tauri / PySide | 本机无 Rust/.NET；Electron 对透明窗+点击穿透+托盘的成熟度最高 |
| D2 | 插件走外部目录 + 热加载 | 用户要求「后续可根据我的想法和需求对桌宠新添功能插件」 |
| D3 | 形象先做、功能后做 | 用户要求「先生成一个像素风的形象让我筛选」 |
| D4 | 形象选定 `chibi`（大头圆身） | 用户在 `preview/index.html` 三方案中选 chibi |
| D5 | 精度按参考图提升到 72×68 | 用户提供 `Picture/ref/pixel_ref.jpg` 作参考，要求「像素可以更精致些」 |
| D6 | 走路改 6 帧、尾巴改 9 段锥形曲线 | 用户反馈「走路时四肢不太明显，尾巴可以更灵动些」 |
| D7 | 两种行为模式都做，程序内切换 | 用户：「两种模式都做，在程序中可以任意切换」 |
| D8 | 暂停/继续、倍率 2/3/4/6×、双产物分文件夹 | 用户会话 2 的要求 |
| D9 | ~~桌宠窗口做成整屏透明覆盖层~~（历史方案，已被 D12 取代） | 当时为覆盖全屏取值；会话 4 已改为随猫小窗，本版不再采用覆盖层 |
| D10 | 暂停时**仍可右键**，只是屏蔽摸头/拖拽 | 暂停后仍要能打开菜单继续运行（第一版做成了完全不可交互，已修） |
| D11 | 用 `app.setName('CalicoPet')` 统一 userData 目录 | 否则 `electron .` 与打包后的配置目录不同，还会留下 `%APPDATA%\desktop-pet` 垃圾目录 |
| D12 | 随猫透明小窗 + 内容区坐标 + 原生 `setShape` | 避免全屏覆盖和全局忽略鼠标卡死；位置回传带 `seq` 丢弃旧帧，解决高 DPI 快速移动的双影/残底 |

### 走过的弯路（避免重复）

| 弯路 | 结论 |
| --- | --- |
| 用固定裁剪框从照片取色 | 框位靠肉眼估算，反复漂移采到壁纸 → 改用**颜色分桶 + 掩码可视化核验** |
| 用圆斑（`spots`）画三花斑 | 花斑糊住眼睛和口鼻 → 改为**遮罩式区域绘制**：先按几何区域上色，再在中央把白筋/口鼻刷回来，且只在头部轮廓内作画（`repaint_inside`） |
| 遮罩重绘不限制范围 | 白筋刷到背景上（出现竖线）→ `Canvas.repaint_inside` 只覆盖已上色像素 |
| 初版用纯程序化几何画脸 | 眼睛浮空、口鼻被覆盖 → 眼睛必须**先铺眼睑暗环再画虹膜**；口鼻区域最后刷白 |
| 参考图直接读取失败 | 该文件扩展名 `.png` 实为 **JPEG**，已复制改名到 `Picture/ref/pixel_ref.jpg` |

## 4b. 环境坑与解决（重要，后续对话会用到）

本机的沙箱与网络环境有几处会反复踩的坑，已全部在脚本里绕过：

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `npm install` 报 `spawn EPERM` | 沙箱禁止带管道的子进程（Electron postinstall 要拉子进程） | `npm install --ignore-scripts`，再用 `scripts/electron-install.ps1` 单独装运行时 |
| npm 缓存写入 `%LOCALAPPDATA%\npm-cache` 被拒 | 用户级缓存目录不可写 | 项目内 `.npmrc` 设 `cache=.npm-cache` |
| Electron 下载慢/失败 | 官方源在国内慢 | `scripts/electron-install.ps1` 与 `scripts/pack.ps1` 设 `ELECTRON_MIRROR` 为 npmmirror |
| **不要把 electron 的键写进 `.npmrc`** | npm 不认识 `electron_config_cache` / `ELECTRON_MIRROR`，每次命令都在 stderr 报警告，而 `$ErrorActionPreference='Stop'` 会把警告当致命错误 | 只在 `.ps1` 脚本里设环境变量 |

### 4d. 窗口架构变更（重要！点击问题最终解法）

**问题**：用户报告"无法拖动、点击没反应"，两次修复都没解决。

**排查过程与结论**：
1. 第一版猜测是 `setIgnoreMouseEvents(true, {forward: true})` 在 Windows 上把窗口卡在穿透模式 → 去掉 `forward`，加光标轮询 + 像素级上报 → 用户仍然点不动。
2. 我尝试用真实鼠标点击做端到端验证，但**自动化会话无法驱动交互桌面**（`SetCursorPos` 对应用所在会话无效，detached 进程也不行），所以始终无法证实。
3. 最终放弃继续猜测，做**结构性修复**。

**新架构**（取代原来的整屏透明覆盖层）：

| | 旧方案 | 新方案 |
| --- | --- | --- |
| 窗口 | 覆盖整个工作区的透明层 | **只有猫那么大**（精灵 + 6px 边距），跟着猫移动 |
| 输入 | 持续切换 `setIgnoreMouseEvents` | **完全不需要**切换；点到猫就是点到窗口 |
| 点击穿透 | 靠光标轮询 + 遮罩判定 | 天然成立：窗口之外就是桌面 |
| 坐标系 | 窗口=屏幕，单一坐标系 | 渲染器内部用**工作区坐标**（world），绘制时用 world − windowRect 换算；主进程按渲染器上报的位置移动窗口 |

代价：窗口在猫周围有 6px 的不可穿透边距（点到那里会被窗口吞掉）。换取的是**没有任何脆弱的输入模式切换**。

**关键实现点**（改这块代码前务必读）：
- `src/main/main.ts`：`SPRITE_NATIVE` / `WINDOW_PAD` / `spriteSize()` / `windowSize()` / `moveWindowToAnchor()` / `homeAnchor()`；窗口创建时 `setIgnoreMouseEvents(false)` 且**永远不要再打开**
- `src/renderer/renderer.ts`：`windowRect` / `workArea` / `applyFrame()`（窗口移动时平移宠物，保持屏幕位置不变）；`layoutCanvas()` 把画布放到 `pad` 偏移处；`reportPosition()` 每帧上报，主进程据此移动窗口
- 输入：`beginDrag/updateDrag/finishDrag` 是纯函数，`window.__petTest` 暴露给自动化测试；**不再有任何 interactive 标志判断**

### 4e. 坐标系统一（第二次窗口重构后必须遵守的规则）

重构为"小窗口跟随猫"之后出现了一轮坐标混乱，症状是**猫只能在屏幕右下角被点中/拖动、拖动时疯狂抽搐、跟随模式只在右下角生效**。根因是同一个坐标系被混用了：

| 位置 | 曾经错在哪 |
| --- | --- |
| `defaultHome()` | 用**原生**像素宽算位置（漏乘倍率），落点随倍率偏 |
| `pet.restore()` | 传入的是**世界坐标**，但控制器区域是窗口坐标，clamp 后宠物被放到窗口外 |
| `hitTest()` | 用世界坐标（工作区）判定，而遮罩是窗口坐标 → 判定区整体偏移 `windowRect`（约 2276×1182），正好只与屏幕右下角重合 |
| 拖拽 | 指针用窗口相对坐标，而窗口正在跟着猫移动 → 窗口位移被反馈进拖拽计算 → **抽搐** |

**统一后的规则（改这块代码前务必遵守）**：

1. **控制器 `PetController` 一律使用工作区（world）坐标**。`pet.x / pet.y` 是猫脚底在屏幕上的位置。
2. **指针事件坐标必须先转成屏幕坐标**：`e.clientX + windowRect.x`。拖拽 API (`beginDrag/updateDrag/hitTest`) 的参数都是屏幕坐标。
3. **只有绘制和遮罩构建使用窗口坐标**：`localAnchor() = pet - windowRect`，再加 `pad` 偏移得到精灵局部坐标。
4. `applyFrame()` 只更新 `windowRect/workArea`，**不移动宠物**（是窗口跟着猫，不是猫跟着窗口）。
5. 诊断里 `pos` 是**世界坐标**，`windowRect` 是窗口矩形；两者之差应等于 `pad + 精灵中心偏移`，可用这一点快速自检。

**防回归用例**：`hit-test`（猫身中心必须命中、边距必须不命中）、`drag-moves`（额外断言**落点**与放下位置一致 `landedAt`）、`drag-path`（指针与猫位移必须 1:1，且不能有回退步）、`smooth-roam` / `smooth-follow`（窗口运动方向反转次数与单次步进上限）。

### 4f. 窗口跟随：死区策略（消除"抽搐"）

**症状**：拖动时猫疯狂抽搐；跟随模式只在屏幕一小块区域生效。

**根因**：窗口每帧调用 `setBounds()` 跟着猫移动。窗口在指针下方重新定位会让 Windows 为**没有真正移动过的光标**补发 mouse-move 消息，而这些消息在拖拽过程中被当作新的指针位置 → 窗口自身的位移被反馈进拖拽计算 → 正反馈 → 抽搐。跟随模式同理：窗口移动不断改写指针的窗口相对坐标，导致跟随时断时续。

**解法（`renderer.ts` 的 `reportPosition`）**：
1. **死区跟随**：猫在窗口内部自由移动，只有偏离窗口中心超过 `FOLLOW_FRACTION = 0.15` 个精灵尺寸时才上报一次，让主进程重新居中窗口。窗口移动时同时保持猫的屏幕位置不变，所以视觉上猫是静止的，只有透明边距在换位置。
2. **`setPosition` 而不是 `setBounds`**：每帧调用时 `setBounds` 会重做定位+改尺寸，明显更重。
3. 实测：窗口移动次数降为每 30~35px 一次（原来每帧），方向反转 0 次。

**注意**：死区会让"窗口位置"与"猫位置"不再逐帧同步，这是**刻意**的。判断是否需要上报必须与**上次上报时记录的猫位置**比较，而不是与当前位置比较 —— 后者在重新居中后有一帧是陈旧的，会吞掉下一次上报。

**验证手段的边界（重要）**：自动化会话无法驱动交互桌面（`SetCursorPos`/`SendInput` 对应用所在会话无效，detached 进程也不行），所以**真实鼠标点击/拖动无法自动验证**。能自动验证的是：命中判定、拖拽逻辑（经 `window.__petTest`）、窗口位移平滑度。真实输入只能由用户确认。

### 4g. 抽搐的真正主因：动画帧在整身平移（用户提供录屏后定位）

用户提供了 23 秒录屏，由此**直接量到**了问题，不再依赖推测。

**录像分析结论**（`tools/track_pet.py`、`tools/filmstrip.py`）：
- 全片**只有一只猫**（排除了"存在第二个实例"的猜测）
- 猫在底部平滑移动，步进稳定在 -120/-148/-133/-107/-183 px，方向反转仅 3 次 —— **窗口跟随本身是平滑的**

**真正的根因在动画本身**：`Params.breath` 会让整个身体上下平移 4~5 像素，导致待机循环的第 0/1 帧有 **19.4% 的像素不同**、`carry` 有 **21.1%**。也就是说猫**每一帧都在整身跳一下**。用户看到的"疯狂抽搐"就是这个，与窗口无关。

**修法**：
1. **`breath` 不再平移身体**（`tools/chibi_hd.py`）。呼吸改由渲染器做画布层的极小缩放（高度变化约 2~3px），只动下缘、轮廓居中：
   ```ts
   ctx.translate(0, h); ctx.scale(1 - breath*0.004, 1 - breath*0.012); ctx.translate(0, -h);
   ```
2. **走路循环接缝修正**。原序列是 `[0, 1, 0, -1, 0, 1]`：最后一帧"迈右腿"直接接第一帧"迈左腿"，**一帧内对调双腿并让头跳 1.5px**。改为真正的中立位循环 `[0, 1, 0, 0, -1, 0]`，尾巴摆动保持正弦以跨过接缝。
3. 走路时的头部摆动减半（`gait * 0.5` → `0.25`），眼神偏移也收小。
4. `carry` 的两帧摆动幅度收小（原来是两个明显不同的姿势）。

**效果**（帧间差异，opaque 像素占比）：

| 动画 | 修前 | 修后 |
| --- | --- | --- |
| sit 待机 | 19.4% | **3.7%** |
| carry 被拎起 | 21.1% | **8.4%** |
| walk 循环接缝 | 是全部转换中最大的一处 | **全部转换中最小的一处**（头部仅 108px） |

**新增自动守卫**：`tools/check_frames.py`
- 判据一：非姿势类动画（sit/sleep/carry）单帧变化不得超过 sprite 的 15%（否则说明"不是在原地呼吸，而是在跳"）
- 判据二：**循环接缝不得是异常值**（`seam / median ≤ 2.5`）—— 走路这类腿本来就要大幅摆动的动画，用接缝比值判断才正确
- `pat` 是一次性动画，不检查接缝

**录像分析工具**（保留备用）：`tools/track_pet.py`（按配色定位猫的轨迹）、`tools/filmstrip.py`（以猫为中心抽帧成影像条）、`tools/zoom_video.py`、`tools/frames_video.py`。下次有录屏时先跑这些，比猜快得多。

### 4h. 跟随鼠标：必须用全局光标（架构修正）

**症状**：跟随模式只在屏幕部分区域生效（用户第二次反馈：「只能在部分区域追踪鼠标而非整个屏幕」）。

**架构症结**：渲染器要知道鼠标在哪，靠的是 `pointermove` 事件 —— 而**这些事件只有当鼠标位于猫窗口（240×216）内才会送达**。窗口外的光标，渲染器一无所知。这是死结，靠调参数无解。

**修法**：光标位置的权威来源改为**主进程**。`screen.getCursorScreenPoint()` 能读全屏任意位置的光标，与窗口无关。

```
主进程 syncCursorPolling()
  └─ follow 模式且未暂停时，每 40ms 推送一次  ──IPC pet:cursor──▶  渲染器
                                                                  cursor = pos
其他模式不轮询（省电）：拖动/点击本来就有窗口内的事件
```

**踩到的三个坑**（都留了注释，避免重犯）：

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| `syncCursorPolling()` 只在 `applyConfig` 里调用，而那时 `win` 还是 null | 轮询**从未启动**，跟随退回陈旧值 | 在 `did-finish-load` 里也调用一次（窗口此时才存在） |
| 主进程做了"位置未变就不重发"的去重，渲染器却有"超过 500ms 视为过期"的回退 | 鼠标一停下，渲染器就回退到陈旧的 `pointer`（初值 0,0），**猫全速冲向屏幕角落** | 跟随模式**一律使用最后一次已知的全局光标**；鼠标静止 = 猫待在原地（本就正确）。用 `haveCursor` 标志代替时间戳判断 |
| 用假光标做测试时，主进程读到的始终是 (0,0) | 误判为"喂数据没通" | 其实是上面的回退逻辑在作祟；同时给主进程加了 `cursorStats`（polls/sent/skipped）便于区分"没读到"和"读到了但没送" |

**防回归用例**：`follow` 探针把假光标先后放到工作区最左和最右，轮询等待猫到达（各给 16s，覆盖 2160px），断言误差 < 30px。实测两侧误差均 14px（打包版 19/28px）。

**独立验证脚本**：`scripts/verify-follow.ps1`（约 35 秒，不放进常规套件）。

**顺带说明**：猫只沿地面水平跟随（`controller.behave` 只改 x）。**这条在会话 6 已被取代** —— 见 §4j。

### 4j. 跟随改为二维 + 拖拽回归（会话 6）

用户要求：「跟着鼠标上下移动，沿直线走向鼠标当前位置」，同时报告「现在拖动不了猫了」。

**① 跟随改为二维（斜向直线走向光标）**

原实现只在 `behave()` 里改 `x`，是纯水平跟随。改为 `chase()`：

```
targetX = cursor.x
targetY = cursor.y + spriteH * (1 - hoverFollow) / 2    // 光标落在猫身偏上位置
dx, dy  = target - 当前位置
speed   = min(followSpeed, dist * 6)
按 dist 归一化后按比例同时推进 x 与 hover
dist <= followArrive(26px) → 停下并切 sit
```

**关键设计：`y` 恒等于地面线，上下移动全部由 `hover` 承担。**

第一版试图直接改 `pet.y`，结果被重力状态机抢走控制权 —— 落地判定反复把 `y` 重置回 `groundY`，实测出现 `petY = 3492` 这种荒谬值（超出屏幕）。改为：

| 量 | 含义 |
| --- | --- |
| `y` | 恒为地面线脚底位置，只有重力/拖拽会改 |
| `hover` | 视觉抬升量（像素），跟随模式专用，`clampHover()` 限制在工作区内 |
| `drawY` | `y - hover`，**渲染、命中检测、窗口定位全部使用它** |

配套改动：
- `visualX / visualY / drawY` getter；渲染器的 `localAnchor()`、`hitTest()`、`reportPosition()`、`persistPosition()`、诊断 `pos/hitBox` 全部改用视觉位置
- `mode` 改为 getter/setter：**离开 follow 时把 hover 归零**，否则猫会卡在半空
- `dragTo()` 接收视觉位置，`endDrag()` 从视觉位置开始落体

**② 拖拽回归：`pointer-events: none`**

我在简化 `renderer.css` 时给 canvas 留了 `pointer-events: none`，导致 **canvas 永远不会成为事件目标**，拖拽静默失效。改为 `auto`。

**新增防回归用例 `dom-target`**：断言 `document.elementFromPoint(画布中心)` 返回 canvas、`pointer-events !== 'none'`、且在 canvas 上派发的 `pointerdown` 能冒泡到 window 监听器。这类 **CSS 回归是逻辑层探针抓不到的**，必须从 DOM 层验证。

**验证**：`tools/probe_follow_2d.py` 定量记录 —— 光标固定在高处时，猫的 `hover` 从 204 升到 252、`drawY` 从 1392 降到 1140，**斜向朝目标移动**；常规套件 14/14 通过。

### 4k. 竖直跟随的符号陷阱（会话 6 踩了三次）

竖直跟随改了四轮才对，每一轮都是同一类错误：**世界坐标 y 向下增长**，而 `hover` 被定义为"抬升量"（向上为正），两者符号相反。

| 轮次 | 错误 | 症状 |
| --- | --- | --- |
| 1 | 直接改 `pet.y` 做垂直跟随 | 重力状态机的落地判定反复把 `y` 重置回地面线，实测 `petY = 3492`（屏幕外） |
| 2 | 改为只动 `hover`，但 `clampHover` 的 `minHover` 算成了 `y - bottomEdge`（=204） | hover 被**向上钳到 204**，无法下降 |
| 3 | 目标位置按"光标=脚底"算 | 屏幕下半部的光标推出超出范围的 `drawY`，钳位后宠物原地不动 |
| 4 | `hover += dy * step` | 目标是上方（`dy<0`）却让 hover **减小** → 背向光标移动；最终改为 `hover -= dy * step` |

**现在的定义（改这块前务必对齐）**：

```
y      = 脚底的世界坐标（地面线上，只有重力/拖拽改它）
hover  = 抬升量，向上为正 → drawY = y - hover
drawY  = 精灵底边的世界坐标（渲染/命中/窗口定位都用它）
钳位    = hover ∈ [y - (area.y + area.height - spriteH), y - area.y]
跟随目标 = 让精灵**中心**落在光标上 → targetDrawY = cursor.y + spriteH / 2
```

**教训**：在有符号的坐标系里，"目标位置"和"位移量"要分开推导，不能共用同一个公式。第 2、4 轮的根因都是没有先写下 `drawY = y - hover` 这条约定。

**顺带修掉的拖拽回归**：`renderer.css` 里 canvas 的 `pointer-events: none`（我简化 CSS 时留下的）使 **canvas 永远不会成为事件目标**，拖拽静默失效。改为 `auto`，并新增 `dom-target` 用例断言 `elementFromPoint(画布中心)` 返回 canvas。

**调试方法**：这轮靠"把中间量打出来"收敛 —— 给控制器加临时的 `debugState`（面积/精灵高/钳位上下界）和 `lastCalc`（`dy / step / hoverBefore / hoverDelta / hoverAfterAdd / hoverAfterClamp`），一眼就看到 `hoverAfterAdd=198.4 → hoverAfterClamp=204` 被钳住、以及 `dy<0` 却让 hover 减小。**排查这类问题时，先把中间量打出来比读代码快得多。**

### 4m. 位置模型重做：全屏二维移动（会话 8）

用户报告两个问题：**任何模式下长按鼠标都拖不动桌宠**；**跟随模式到不了屏幕最下方**，且**自由走动只在最底部横向移动**。两条都源自同一个旧模型。

#### ① 旧模型为什么做不到（改这块前先读）

旧模型把"位置"拆成两个量：

```
y     = 脚底，恒等于地面线（groundY）
hover = 抬升量（只能向上），实际绘制位置 = y - hover
```

后果：

| 症状 | 根因 |
| --- | --- |
| 跟随到不了屏幕最下方 | `clampHover` 下界 = `y - (area.y + area.height - spriteH)`，猫最矮只能"脚落在工作区底边"；而 `chase()` 还把目标定成"精灵**中心**对准光标"，光标越靠下越要求更靠下的位置，被钳位后就不动了 |
| 自由走动只在底部横向走 | `behave()` 只改 `x`，`y` 永远是地面线 |
| 拖拽方向错、位移被吞 | `dragOffset` 用**地面坐标 `pet.y`** 计算，而猫画在 `drawY`；`dragTo()` 又把屏幕 y 反算成 `hover`，向下拖被"抬升量"吃掉 |

#### ② 新模型（唯一约定）

```
x, y  = 精灵**底边中心**在**工作区坐标**中的位置，可在整个工作区内自由取值
groundY = area.y + area.height   （地板 = 工作区底边，不再是它上面 6px）
重力只在"掉落"时生效：拖拽松手 / 退出跟随模式且悬空
hover 改为只读派生值（groundY - y），仅为诊断与历史探针保留字段形状
```

`clampToArea()` 是唯一的越界护栏：`x ∈ [area.x + w/2, area.x + area.width - w/2]`、`y ∈ [area.y + spriteH, area.y + area.height]`，任何倍率下精灵都完整留在屏内。

**三种模式的新语义**：

| 模式 | 垂直行为 |
| --- | --- |
| 跟随 `chase()` | 二维直线走向光标；目标取"光标处"但**钳进可达范围**（精灵中心对准光标、底边不越界）——既能贴到屏幕最下方，也不会把身子探出屏幕 |
| 自由走动 `wander()` | **随机直线漫步**：全屏合法带内随机取点（高度在高处/地面之间交替），以 `roamSpeed` 直线走过去，到达后停顿 0.5~1.6s 再取新点。无跳跃、无重力 |
| 原地待机 | 不动；掉落后的落地回弹仍保留 |

#### ③ 拖拽修复（四个独立缺陷）

| # | 缺陷 | 修法 |
| --- | --- | --- |
| 1 | 抓取偏移用地面坐标算 | 改用**视觉锚点** `pet.visualX/visualY`，猫不再在按下瞬间跳位、方向也正确 |
| 2 | 指针快速滑出 240×216 小窗口后收不到 `pointerup` → `dragging` **永久卡 true**，之后完全点不动 | `setPointerCapture` 接管指针；再加 `pointercancel` / `blur` / `mouseleave` 兜底 |
| 3 | 再兜一层：渲染主循环**看门狗**（1.5s 无拖拽事件即结束拖拽） | `loop()` 内 `if (dragging && now - lastDragAt > 1500) finishDrag()` |
| 4 | 静默失效：`playTransient('land')` 没有对应动画（只有 sit/blink/walk/sleep/pat/carry/angry） | 硬着陆改播 `angry` 两帧，并在代码里注释这个坑 |

#### ④ 自由走动的最终形态：直线随机漫步（用户决定，会话 8）

**结论先行**：自由走动 = **在全屏范围内随机取点，走直线过去，停顿片刻，再取下一个点**。没有跳跃、没有重力。这是用户在看过跳跃版本后明确定的（「不需要随机跳跃功能，移除掉，能在自由走动模式下随机直线移动即可」）。

下面这张表记录的是**做跳跃版本时走过的四次弯路**，全部已从代码中删除，留档只为避免以后有人再想加跳跃：

| 弯路 | 实测现象 | 为什么不行 |
| --- | --- | --- |
| 目标更高就原地向上跳 | 34s 内 **233 次跳跃**，顶点恒为"地面 − 260"（`roamHopMax`），只覆盖 **2/8** 高度带 | 单跳上限 260px，而**必须落地才能再跳** → 永远弹回原高度 |
| 先爬到目标高度再横向走 | 同样 2/8 | 爬升时水平被冻结，而"到达"要求两轴同时满足 → 永远到不了 |
| 走到目标下方再跳一次 | 2/8 | 一跳够不到 365px 以上的目标 |
| 空中连跳（每跳升 240px） | 覆盖过 3/8~7/8，但**极不稳定**；跳跃数高达 230~327 次/34s（≈7~10 跳/秒，视觉像弹球） | 组合爆炸：跳跃预算、起跳横向门槛、连跳被打断、落地重置互相影响，加固一处就在别处出问题 |

**最终实现**（`controller.ts` 的 `wander()` / `chooseRoamTarget()`）：

```
每段漫游：随机取目标点 (x, y)
  x ∈ [area.x + w*0.6, area.x + area.width - w*0.6]
  y ∈ 合法带内，且「高处」与「地面附近」交替抽取（roamHigh 翻转）
移动：每帧朝目标直线推进 roamSpeed(115px/s)，两轴同时插值
到达（距离 ≤3px）：停顿 0.5~1.6s → 抽下一个目标
```

**为什么高度要交替而不是纯随机**：纯均匀随机会让大多数目标落在地面附近，于是某个 34 秒窗口里猫可能一直在底部走 —— 实测覆盖在 **1/8 到 8/8** 之间乱跳。交替抽取让"全屏探索"成为结构性行为而非运气。

**实测（连续三次，dev 构建）**：

| 运行 | 高度带 | 离地最高 | 单帧最大垂直位移 | `ok` |
| --- | --- | --- | --- | --- |
| 1 | **7/8** | 959px | 8px | ✅ |
| 2 | **7/8** | 1000px | 6px | ✅ |
| 3 | **8/8** | 1101px | 5px | ✅ |

`maxStepY` 只有 5~8px，说明确实是匀速直线滑行，没有任何弹射成分。

**关键代码点**：`controller.ts` 的 `wander()` / `chooseRoamTarget()` / `chase()` / `clampToArea()` / `land()`；`renderer.ts` 的 `beginDrag/updateDrag/finishDrag`、`loop()` 看门狗、`wireInput()` 的指针捕获。

#### ⑤ 新增回归用例

| 用例 | 断言 | 为什么必须有 |
| --- | --- | --- |
| `drag-pointer` | 用**真实 DOM 指针事件**驱动（pointerdown → 甩到窗口外 200px → pointermove → 不发 pointerup 就松手）；断言猫与指针 **1:1** 位移、松手后**不卡 dragging**、之后仍能"摸头" | 旧的 `drag` 探针只调 `window.__petTest`，看不到抓取偏移错、指针捕获缺失、`dragging` 卡死这三类问题 |
| `roam-vertical` | 34 秒内访问 ≥4 条高度带（每条 150px）**且**到达屏幕上半部 | 旧的 `smooth-roam` 只看水平位移，"贴底漫游"时它照样通过 |
| `smooth-roam` | 方向反转 ≤8；垂直单步上限放宽到 260（跳跃是刻意的大位移） | 原来的 70px 上限会把正常跳跃误判成抽搐 |

**探针自身踩过的坑**（写新探针时注意）：把**世界坐标**与**屏幕坐标**直接比较会产生"幽灵误差"（本例 102px，正好是半个精灵高）——窗口会跟着猫移动，同一个屏幕点在窗口移动后对应不同的世界点。**断言必须用同一坐标系内的位移或绝对世界位置**。

**另一类坑：用"位移跨度"衡量"是否在动"不可靠**。自由走动在目标点会休息 0.5~1.6 秒，休息恰好落进 2.6 秒采样窗口时 `spanX` 会读到 2px，看起来像"没动"。改为统计**累计路程**（`pathX`）后稳定。

**还有一类：`paused` 冻结与画面读取的竞态**。想在"动画冻结时读像素"必须在同一状态内完成，固定的 `setTimeout` 会与配置往返赛跑（实测同一朝向读到两种结果）。

**采样陷阱**：250ms 级轮询会**系统性错过跳跃顶点**（一跳约 1s），看起来像"猫静止不动"；50ms 采样 + 逐帧滚动日志才看清轨迹。

**② 沙箱：Electron 无法在受限会话内启动（与代码无关）**

复核 M1/M2 时必须跑 Electron，而在 `workspace-write` 受限模式下会失败，且**报错具有强误导性**：`smoke.ps1` 只会打印"no log produced / FAIL: no log output"，看不出真因。手动前台启动才看得到：

ERROR:process_singleton_win.cc(465) Lock file can not be created! Error code: 5
FATAL:platform_channel.cc(89) Check failed: . : 拒绝访问。 (0x5)

### 4n. 走路速度三档 + 朝向修正（会话 8 续）

#### ① 走路速度：菜单三档，当前速度为"中"

| 档位 | 速度 | 说明 |
| --- | --- | --- |
| 慢 | 55 px/s | |
| **中** | **115 px/s** | 默认，即此前固定使用的速度 |
| 快 | 210 px/s | |

- 数值放在**渲染器** `controller.ts` 的 `ROAM_SPEED_PX`（主进程只存储/转发档位），因为运动全部归渲染器管；控制器暴露 `roamSpeed` 字段。
- 配置 `roamSpeed: 'slow' | 'normal' | 'fast'`（默认 `'normal'`），随 `pet-config.json` 持久化，菜单「走路速度」单选项切换。
- 回归用例 `speed-slow/normal/fast` 读渲染器实测的**每帧实际位移速率**（`diagnostics.speed` = 帧内位移 ÷ dt），直接断言 55 / 115 / 210；与漫游停顿节奏无关，因此短且稳定。

#### ② 朝向修正：`facing` 语义反了

**症状**（用户报告）：向左走时朝右、向右走时朝左 —— 完全镜像相反。

**判定原生美术朝向的证据**（不靠猜）：取"下半身（含尾巴）水平重心 vs 上半身（头胸）重心"，五个动作帧一致为 上半身 209.5px、下半身 257.7px（456px 宽画布）→ **尾巴在右、头在左，原生贴图朝左**。判据脚本：`tools/check_facing_metric.py`。

**修法**：语义统一为 **`1` = 朝右、`-1` = 朝左**（直观），绘制时"朝右才镜像"：

```ts
// renderer.ts draw()
ctx.translate(w / 2, 0);
if (pet.facing > 0) ctx.scale(-1, 1);   // 原生朝左，故朝右才翻转
ctx.translate(-w / 2, 0);
```

掩码 `buildMask(frame, pet.facing > 0, …)` 同步，保证**点击命中的就是看到的**。

**顺带修掉**：拖拽/跟随原本完全不改朝向（`dragTo` 里没有 facing 逻辑），拖着猫往右走它还朝左。现在拖拽按拖动方向转向；"回到右下角"改为朝左（`facing: -1`，朝屏内）。回归并入 `drag-pointer`：拖左必须 `-1`、拖右必须 `+1`。

**旧配置迁移**：旧版本把 `1` 当"朝左"，照读会继续反向，所以 `coerce()` **只接受 `-1`**（含义未变），`1` 一律落回默认（朝右）——见 `config.ts` 里 `facing` 字段的注释。

#### ③ 事故与守卫：PowerShell 重写源文件会毁掉中文（重要）

**事故**：为删除一段探针，我用 `Get-Content` + `Set-Content -Encoding UTF8` 重写了 `src/main/main.ts`。Windows PowerShell 5.1 的 `Get-Content` 默认按**系统 ANSI 代码页**解码，UTF-8 中文被当 GBK 读入再以 UTF-8 写出 —— 17 行中文全变乱码，部分字节丢失成 `?`，**连字符串闭引号一起被吃掉**。`tsc` 报 "Unterminated string literal"，编译产物里 `'慢'/'中'/'快'` 成了坏字符串，主进程加载即崩（用户看到 "A JavaScript error occurred in the main process"）。

**修复**：`tools/repair-strings.py` —— **不猜乱码字节**，按每行的 ASCII 骨架（`['rest', '…'],`、`label: '…',`、`tray.setToolTip('…')`）整行重写；每条规则必须恰好命中一次，否则拒绝写入。15 行 + 托盘提示一次修好。

**防线（可回归验证）**：`scripts/check-text.mjs`，已接入 `npm run build` 第一步：

| 检查 | 抓什么 |
| --- | --- |
| UTF-8 BOM | `Set-Content -Encoding UTF8` 留下的 BOM |
| U+FFFD | 已经发生有损解码 |
| 乱码字符集 | 本次实际出现的 GBK 乱码字（**只查代码文件**；文档要能讨论这次事故，故豁免） |
| 行内未闭合的单引号串 | **丢引号**这一类。引号计数不可靠（删一个引号后，后续参数的引号仍可能凑成偶数），故用逐字符状态机扫描，并正确跳过块注释、`//`、模板串、普通字符串与 Python 文档字符串 |

`scripts/check-text-negative.mjs` 是它的**反向测试**：把乱码与丢引号分别注入源文件的临时副本，断言守卫确实报错并点名，随后删除临时文件并确认真实源码仍通过。**抓不到损坏的守卫毫无价值**，所以这一步不能省。

**教训（务必遵守）**：**永远不要用 PowerShell 的 `Get-Content`/`Set-Content` 读写项目源文件**。需要批量改动就用编辑工具，或 Node/Python 脚本并显式指定 UTF-8。

#### ④ 真实鼠标拖不动的真因：窗口位置没有回传给渲染器（会话 9）

**症状**：用户报告"任何模式都不能长按左键快速拖拽"，而我此前的合成事件测试**全部通过**。

**根因（实测数据，不是推测）**：

| 项 | 值 |
| --- | --- |
| 渲染器缓存的窗口位置 | `(2276, 1182)` —— **从启动起从未变过** |
| 窗口真实位置 | `(1911, 278)` |
| **偏差** | 垂直最大 **904px**、水平最大 **459px** |

渲染器把指针的客户端坐标换算成屏幕坐标时用的就是这份缓存（`screenPos()` → `hitTest()`），而它只在启动 / 换倍率 / "回到右下角"时更新；**窗口跟着猫移动时从未被通知**。于是按下的一刻命中判定在几百像素之外，`beginDrag` 直接返回 false —— 拖拽根本不会开始。漫游模式窗口一直在动，所以"任何模式都拖不动"。

**为什么之前的测试没抓到**：`drag-pointer` 探针用 `clientX/Y - windowRect` 构造事件，**正反用了同一份缓存**，误差被自洽地抵消了；而它随后只调 `__petTest` 的拖拽函数，不经过真实命中判定。这是"测试用了被测对象自己的错误假设"的典型陷阱。

**修法**：主进程每次移动窗口后把新位置回传渲染器。

```
moveWindowToAnchor()  ──pet:pos──▶ 主进程 setPosition()
                      ◀─pet:windowMoved {x,y}─  渲染器更新 windowRect
```

主进程另有 `moveStats {requested, sent, deduped}` 便于确认回传确实在发。

**回归用例 `window-sync`**：在**漫游（窗口持续移动）**过程中读渲染器的 `windowRect` 与主进程 `getBounds()` 比对，断言偏差 ≤ 60px。修复前实测 904/459px，修复后 **22/12px**（残余是窗口移动与通知非原子造成的一两帧延迟）。

**调查中的两个陷阱**（都记下来避免重犯）：
1. `window.__petDiag` 是**最多 250ms 前的快照**（除非打开 `__petTrace`），用它读实时位置会得出错误结论 —— 我因此一度误判"回传没生效"。
2. 直接在桥上加一个裸监听器计数，是区分"没发 / 发了没到 / 到了但业务回调没跑"的最快手段（实测收到 64 条）。

#### ⑤ "显示倍率"显示成"2脑"：同一编码事故的第二处残留

`label: \`${value}×\`` 里的 `×`（U+00D7，UTF-8 字节 `C3 97`）在 §4n③ 那次 PowerShell 事故中被按 GBK 解读成日文汉字 **`脳`（U+8133）**。我的修复表只覆盖了 15 个已知菜单行，漏掉了这一行；乱码检测的字符集也没包含 `脳`。两处都已补上（源码改用 `\u00d7` 转义，彻底避免再被误编码）。

**教训**：编码事故后的排查必须**逐字符核对所有非 ASCII 字符**，不能只修"看得见的那些行"。

#### ⑥ "回到右下角"无效 + 新增"被拎起后颈"动作（会话 10）

**① `回到右下角` 为什么没用**

`renderer.ts` 的 `onRecenter` 里还留着**旧模型的坐标换算**：

```ts
pet.restore(home.x - windowRect.x, home.y - windowRect.y, 1);   // 错
```

`defaultHome()` 返回的已经是工作区（世界）坐标，`restore()` 要的也是世界坐标，再减一次窗口左上角就把猫放到了屏幕外，随后的区域钳位又把它拉回原处 —— 表现为"点了完全没反应"。改为直接传世界坐标（并把朝向设为 `-1` 朝屏内、立即持久化）。

**回归用例 `recenter`**：先把猫拖到 (500,1100)，调用真正的菜单动作，断言回到 home 的距离 < 40px。实测 **0px**。

**② 新增动作：被拎起后颈（拖动期间持续）**

用户要求：长按拖动时触发一个"被一只手拎起来"的动作，松手即取消。原来的 `carry` 只有 2 帧、且是**瞬时动画**（0.3 秒就交还基础动画），拖动时猫会自己坐下。

改动分三处：

| 层 | 改动 |
| --- | --- |
| 美术 `tools/chibi_hd.py` | 新增 `hang`（悬挂）/`hang_sway`（钟摆）两个参数，并为悬挂姿势**单独写几何**：身体改为"臀-腹-肩"三个下垂椭圆、四腿从身体下缘垂到地面、尾巴从**臀部**垂落（不是从腹下）。用"拉伸坐姿"的做法失败了两次：先是身体变成超出画布的矩形，再是尾巴从腹部起笔被身体挡住、几乎看不见 |
| 动画 `export_chibi_hd.py` | `carry` 扩到 **6 帧**，摆动走平滑弧线；**眨眼刻意避开掉头那一帧**（同帧既掉头又眨眼实测帧间变化 18.4%，被帧差守卫判为"不是在原地呼吸"） |
| 动画器 `core/animator.ts` | 新增**持续覆盖** `holdOverride`/`releaseOverride`（`Channel.persistent`）：在释放前一直循环，区别于瞬时动画。并修掉一个真 bug：**空闲眨眼会抢走持续姿势**（`playTransient` 现在拒绝打断 `persistent`） |
| 控制器 | `startDrag()` → `holdOverride('carry')`；`endDrag()` → `releaseOverride()` |

**回归用例 `carry-pose`**：开始拖动 → 注入持续移动事件（否则 1.5 秒看门狗会正确地结束拖拽）→ 等 **2.6 秒**（远超动画自身 1.8 秒长度）→ 断言仍是 `override='carry', persistent=true`；松手后断言已释放。实测通过。

**又一课：诊断快照会骗人**。该探针最初读 `window.__petDiag.anim`（每 250ms 才发布、且只在挂了探针时发布），结果在拖动中读到 `override: null`，让我一度以为持有逻辑没生效；改用**实时读取** `window.__petTest.animState()` 后立刻通过。同一类坑在 §4n④ 已经踩过一次（窗口位置），这是第二次。

#### ⑦ 删除「回到右下角」+ 拖拽跟手（会话 11）

**① 「回到右下角」直接删除**（用户要求）

上一版我修好了 `onRecenter` 的坐标换算，回归也显示归位距离 0px，但用户实测**仍然无效**。根因是它与"位置持久化"互相抵消：猫的位置每 700ms 就被写进配置，而菜单项只让"当前这一帧"回到 home，紧接着渲染器又按自己记住的位置上报并覆盖回去；而且 `x/y` 一旦落盘，**重启后猫也不会回到 home**（它恢复到上次保存的坐标）。这个功能的设计本身与持久化冲突，越修越绕，用户决定删掉。

删除范围：菜单项、`recenter()` 函数、`app:recenter` IPC、`preload` 与渲染器 bridge 的 `recenter()`。`pet:recenter` 通道保留但**只服务"移到主显示器"**（改名为 `switchToPrimaryDisplay()`）：切换显示器时把猫放到新工作区的右下角并朝屏内，因为旧坐标属于旧显示器。

**② 拖拽"跟不上鼠标"**

`reportPosition()` 同时受**死区**与**120ms 节流**限制 —— 那是为固定位置场景设计的（防止窗口移动把自身位移反馈进跟随/拖拽回路）。结果是拖动时窗口最多**滞后 120ms** 才跟上，鼠标一快猫就明显落后。

| 改动 | 说明 |
| --- | --- |
| 拖动期间**绕过死区与节流**（`if (!force && !dragging)`） | 每帧立即上报位置，窗口贴着指针走 |
| 死区 `FOLLOW_FRACTION` 0.09 → **0.02** | 窗口只比精灵大 12px（`2*pad`），9% 死区（约 20px）会让精灵先被窗口边缘裁切再补位；2% 恰好留在边距内 |

**实测**：新增的 `lagSamples` 在同一次移动的**同一时刻**比对"渲染器记录的窗口位置"与"窗口真实位置"，三处取样均为 **0px**（修复前拖动中窗口会落后整段行程）。`drag-pointer` 用例现在一并断言 `winDragDrift ≤ 20px`。

**关于测量方法的一课**：这个指标我第一版测出 763px 的"滞后"，其实是**把不同时刻的两次取样相减**（拖动开始时的记录 vs 拖动结束时的真实窗口），量到的是猫走了多远，不是滞后。同一类错误在这个项目里已经出现三次（§4m 的 102px 幽灵误差、§4n④ 的陈旧诊断、这里）——**比较必须在同一时刻、同一坐标系内完成**。

### 4q. v0.3.2 坐姿与携带帧边缘异常像素（会话 14，2026-11-21）

### 4r. 按红圈标注定点清理耳侧与胸腹凸点（会话 15，2026-11-21）

**① 耳侧根因与修复**：`chibi_hd.py` 的 `ear_edge = ear & ~_erode(ear)` 原来把整圈耳廓边缘重涂为 `i`，随后又有外部 `outline`，所以即使删掉重复外环，红圈处仍残留一条窄深边。现在同时计算 `near_head` 与 `exposed`：只有**被头部覆盖且不暴露于透明区域**的耳根连接点才保留 `i`，所有外露耳廓边缘保持原本毛色。左耳必要的连续外轮廓正常保留。

**② 胸腹根因与修复**：红圈中的深点来自下半身外轮廓的四连通短片段，放大后像零散方块，而非连续描边。`Canvas.prune_duplicate_outline()` 新增最终栅格清理：仅删除 `y >= h/2` 区域内四连通长度 **≤4** 的 `L` 片段；较长轮廓、脚底线、五官、胡须、尾巴及脸部描边不动。第一轮守卫还捕获到耳根交界同时接触头部和透明区域的残留点，随后用 `exposed` 条件修掉，没有放宽断言。

### 4s. 全部动画帧统一为连续深黑外描边（会话 16，2026-11-21）

用户查看第二轮定点清理后仍认为有多余像素，明确提出：**所有图像帧最外圈统一用黑色像素围一圈**，减少不同颜色边缘块造成的视觉不适。本轮执行这一方案的收敛版，不再继续逐点猜测：在最终栅格上生成**单层、连续、统一深黑色外轮廓**，补齐斜角连接，但不给内部封闭空隙和浅色胡须描黑边。

**① 统一算法**：`Canvas.prune_duplicate_outline()` 改为 `Canvas.unify_outer_outline()`。先移除旧 `L` 外环，以非空且非 `L/X` 的像素作为内部主体；用八邻域膨胀补齐斜角，再从画布边界对外部背景做四邻域洪水填充，只在外部背景中绘制 `L=(30,25,21)`。这样轮廓只位于最外圈，内部封闭透明空隙不会出现孤立黑点，胡须 `X` 也不会参与主体膨胀。

**② 耳朵与尾巴收敛**：保留耳根 `near_head & ~exposed` 规则，外露耳廓由最终统一外环负责；删除尾巴额外的 `i` 外缘重涂，让尾巴同样只由最终外环描边。坐姿、携带及全部动画帧采用同一算法，不再分别处理耳侧和胸腹短碎片。

**③ 33 帧离线审计**：每帧恰好 **1 个四连通 `L` 外轮廓组件**；外露非 `L/X` 颜色像素、内部封闭空隙 `L` 像素均为 0。旧主体的非 `L/X` 像素保持不变，唯一允许的主体改色是尾巴旧 `i` 外缘恢复原尾巴色板；新增像素只能是最外圈 `L`。33 张原生帧均为 76×68、alpha 仅 0/255，6× 与 1× 最近邻一致；运行帧总计 **45,129 字节**。

**④ 真实运行与完整回归**：`pixel-check` 持久化 `outerOutlineComponents=1`、`exposedNonOutline=0`、`internalOutline=0` 和 `shortOutlineFragments=0`，并继续检查双姿态真实 canvas backing store 的 76×68 源尺寸、DPR=1.5、alpha=255 和调色板外颜色=0。`sit_0.png`、`carry_4.png` 均通过；白底源帧与真实画布图已复核。配置单测 **4/4**、完整行为矩阵 **31/31**、Windows `WindowFromPoint` 原生命中通过；文本守卫反向测试能检测 BOM/U+FFFD，随后源码恢复且正向守卫通过。

### 4t. 修复实际窗口叠帧与高 DPI 采样差异（会话 17，2026-11-21）

用户提供两张实际窗口截图，指出源帧白底预览已经正常，但运行效果仍不像统一黑色外轮廓，并怀疑多帧像素图重叠。进程检查确认当时只有一个正常开发版主实例，并非多个桌宠窗口重叠；问题位于单个窗口的真实 canvas 绘制链。

**① 根因——清除范围错误**：`draw()` 已用 `ctx.setTransform(1,0,0,1,0,0)` 切换到设备像素坐标，却又调用 `clearRect(0,0,canvas.width/dpr,canvas.height/dpr)`。在 150% DPI 下，实际 backing store 为 360×324，却只清除 240×216 的左上区域，右侧和底部旧像素会留给后续动画帧，形成用户判断的多帧叠加。此前专项只验证源帧轮廓和实际画布的 alpha/调色板，没有逐像素比较当前帧，因此漏检。

**② 先让专项复现**：新增 `pixelAudit()` 和 `stalePixels/missingPixels/changedPixels/mismatchedPixels`。增强专项在旧清除逻辑上失败，坐姿检测到 804 个残留像素，携带姿态检测到 5,031 个；同一日志里源帧外轮廓等旧指标仍全部正常，证明“源图正确”不等于“实际窗口正确”。参考副本后来改为在每次真实 draw 的同一时刻、用相同位图与矩形生成，避免后续读取时 sub-pixel anchor/squash 已变化而产生假差异。

**③ 两项修复**：第一，恒等变换下直接 `clearRect(0,0,canvas.width,canvas.height)`，每次清除完整 backing store。第二，主画布使用 `willReadFrequently:true`，与 `maskCanvas` 统一 CPU 像素光栅化路径；这消除了 GPU/CPU 在 1.5× 最近邻采样时对耳尖等孤立源像素选择不一致的问题。绘制目标矩形仍取整到设备像素，原生窗口形状与 2 CSS px 安全边距不变。

**④ 修复后证据**：`sit_0.png` 与 `carry_4.png` 的真实画布均与同步干净参考副本逐像素一致，`stalePixels=0`、`missingPixels=0`、`changedPixels=0`、`mismatchedPixels=0`；原生 76×68、DPR=1.5、alpha=255、调色板外颜色=0、外轮廓=1 等旧断言继续通过。白底复核图为 `dist/smoke/composite-fixed-sit-white.png` 与 `composite-fixed-carry-white.png`。

**⑤ 完整回归**：配置单测 **4/4**、完整行为矩阵 **31/31**、Windows `WindowFromPoint` 原生命中通过。最新性能专项为正常 60 次循环、7 次遮罩构建、7 次轮廓更新、60 次位置报告，省电 23 次循环，暂停计数稳定。开发版使用正常配置重启供用户目视确认；安装包、便携版和正式 SHA-256 仍未生成。

## 6. 后续对话怎么用这份日志

1. **先读本文件**，再看 `PLAN.md`（计划与架构）与 `README.md`（怎么跑、怎么改）。
2. 修改形象 → 改 `tools/chibi_hd.py` 的 `Params` 或几何参数，然后跑：
   ```powershell
   python tools/export_chibi_hd.py      # 重新导出 33 帧 + meta.json
   npm run build                        # 同步进 dist（`npm start` 会自动跑）
   ```
   `art/sprites/chibi-hd/meta.json` 是动画的单一来源；`scripts/sync-assets.mjs`
   会把它和帧一起装配到 `dist/renderer/renderer/sprites/`，并校验每一帧都存在。
3. 加动画 → 在 `tools/export_chibi_hd.py` 的 `ANIMS` 里加一条（标签/fps/循环/参数列表），
   参数直接复用 `Params` 的字段，**不必改渲染代码**。
4. 加功能 → 走插件目录，不改主程序（M3 完成后）。
5. 改完必须验证（不要只靠肉眼看屏幕）：
   ```powershell
   npm run check:text
   npm run test:unit
   powershell -File scripts/smoke.ps1 -Seconds 6
   powershell -File scripts/verify-behaviour.ps1
   ```
   这些命令会启动真实 Electron 窗口；测试通过 `PET_USER_DATA_DIR` 隔离配置。若需验证已确认的发布包，再给 `verify-behaviour.ps1` 传 `-Exe <发布exe路径>`。
6. **每次对话结束前更新本文件的 §4 状态与 §5 时间线。**
